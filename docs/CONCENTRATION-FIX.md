# 60% / 80% / 100% 检查、修复与自动翻译方案

检查日期：2026-10-17。本轮修改仅在本地，没有提交、推送或重新部署，也没有调用翻译服务、上传任何小说或安装模型。

## 具体原因

1. `src/features/translation/types.ts` 的 `TranslationProvider` 只是接口，项目里没有具体翻译提供者；`TranslationPanel.tsx` 目前只有 JSON 模板导出、译文导入和缓存管理。英语浓度滑块不调用任何翻译接口。
2. `ReaderPage.tsx` 只从 IndexedDB `cijing-translations` v1 的 `[bookId, chapterId]` 读取当前章，并检查源哈希。`display.ts` 在60/80没有译文时使用原文，100在译文不完整时也整章使用原文。这是防止用假英文冒充译文的保护，不是滑块写入失败。
3. 20/40可调用341条精选词语规则及200条精确句型；这些无法生成任意小说的上下文译文。高档不能靠放大替换率实现自然英文。
4. localStorage/IndexedDB 属于浏览器来源：本地预览与 GitHub Pages、不同设备/浏览器互不共享。发布代码不会发布原设备的小说和译文；可用设置页完整备份，或同原书结构的译文JSON，迁移到正式网址。重复导入同一本书也会生成新的本地书号，不能假定已自动附上另一份本地书籍的译文。
5. 原比例算法按稳定顺序不断加入整组，直到超过目标；不等长片段可能严重超出60/80，甚至使两档选择相同。一个占全章大部分的译段无法在没有对齐信息时安全切开。
6. 生产 CSP 当前为 `connect-src 'self'`，不存在已配置的外部翻译服务。GitHub Pages 提供静态托管，不执行模型或服务端翻译代码。[GitHub Pages 官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

## 已修复

- 新增轻量句组选取：按非空白原文内容重量，选择与目标最近的可用完整句组组合，不再只向上累加。稳定优先级用于相同权重组合，译句不拆分、不拼装；60/80分别选最接近各自目标的组合，切换时可能改变具体哪些句子使用英文，但同一章、浓度和种子下结果固定。
- 40继续以约20%原文内容的真实整句配合词语替换；整句上限35%，避免整段过大直接变成全英文。未修改词库、原文或数据库版本。
- 100仍要求所有非空文字有真实对应译文；完整缓存使用全部句组，图片保留。空模板、部分译文不能冒充100。
- 显示目标与实际整句覆盖率、可用译文覆盖率；缺失时明确“尚未接入自动翻译”、需要导入及跨网址不会自动同步。正在读取译文时显示加载状态，避免瞬时报告缺失。
- 句组过大导致明显偏离目标时说明原因，建议用现有按句模板提供更细对齐。无法通过本轮程序修复译文本身的流畅度、忠实性或缺少的内容。
- 修复译文导入选择同一个JSON后不能再次触发预览的问题，方便修改文件后重新导入。

新选取器用位集和回溯数组，工作区随当前章原文长度增长，不随整本小说或已下载词库增长。12,000字符时位集约1.5KB，两个回溯数组合计约96KB；这些是运算数组大小，不是整个页面的内存峰值。没有新增依赖或模型。6000个句组/12000字符的本机自动测试通过，不据此宣称所有手机性能相同。

## 本轮验证

- 自动测试140项全部通过，含新增5项选取/覆盖回归测试；TypeScript、生产构建及根路径/仓库子目录静态检查通过。
- 不等长40/30/20/10权重例：60%选取60，80%选取80，保持完整片段；位集31/32/33/63/64/65等边界与穷举结果一致，不复用同一片段。
- 独立来源的内置Chromium、390×844视口：此前导入的原创中文EPUB真实对应译文中，60%显示10个句组、约60%；80%显示14个句组、约80%；100%显示19个句组、100%。这些是现有测试书的人工译文，不是本轮自动翻译，也不会作为任意小说的替代正文。
- 没有译文的《雾海来信》在60/80/100均明确提示，正文保留原文。100%中的glasses点词显示眼镜，不翻页；右边缘翻页、字号26→28px重排、刷新后第3/18页恢复均正常。
- 既有TXT、EPUB、目录/图片、原文位置、词典/收藏及备份回归测试通过。尚未重新完成真实iPhone/Android多引擎验收。

## 推荐的自动翻译路线（设计，尚未实现）

保留GitHub Pages前端，另外建立**Cloudflare Worker + Workers AI免费档**的小型翻译后端。所有手机只发普通HTTPS请求，不需要安装模型；模型在服务商服务器运行。运营者需有Cloudflare账号并配置AI绑定，不能把账号密钥打进前端。

使用已托管的多语言模型作为候选，例如Qwen3-30B-A3B FP8。先用原创小说小样评测人名一致、否定/时态、对话关系、漏译与增译，再决定是否上线；模型存在并不证明小说翻译质量达标。[官方模型页](https://developers.cloudflare.com/workers-ai/models/qwen3-30b-a3b-fp8/)

建议处理流程：

1. 用户主动点击“翻译本章”，清楚看到需发送当前章/必要前文给Cloudflare。导入本地小说的默认动作仍只写本地，不自动发书；不把“原书不上传”扩大解释为启用云翻译也完全不传正文。
2. 前端复用现有句组编号、UTF-16范围和源哈希；发送带完整段落上下文的分组请求，附必要的前章摘要和人物/术语表。根据模型上下文和输出上限分批，不能只按单词请求。前文摘要和人名记忆也应与章节一起版本化缓存。
3. Worker校验来源、正文长度、并发和用量，固定允许的模型和中英翻译任务；调用云模型返回对应ID的英文。原文作为数据，不能允许小说文本把提示改为执行其他任务。CORS允许本站，但**CORS不是防盗用认证**；还需速率限制、总预算、请求大小限制及必要的防滥用验证。小说正文不写应用日志或公共数据库。
4. 客户端验证ID、范围、空译、异常膨胀、输出截断和原文哈希，复用现有译文校验/IndexedDB缓存；只写已确认完整批次。中断可续传，切60/80/100复用同一份译文。100只有完整译文才启用。格式校验无法证明语义忠实，仍须质量验收和纠错入口。
5. 只有显式启动翻译时联网；已缓存章节继续本地阅读。修改原文、模型或术语上下文后使相关缓存失效。跨设备仍用备份迁移，不默认公开个人小说或建立云书库。

## 免费与兼容性限制

Cloudflare目前提供账户级 **10,000 Neurons/天** 的免费额度，免费档超限会失败，更多用量需要升级付费。为保持零费用，应维持免费计划、禁止自动升级/付费回退，额度用完显示稍后重试并继续阅读原文或已有缓存。额度由该账号下使用者共享，不能承诺所有用户不限量翻译长篇小说。[官方额度说明](https://developers.cloudflare.com/workers-ai/platform/pricing/)

GitHub Pages加普通HTTPS后端请求在现代iPhone/Android浏览器是现实可行的架构；仍需实际验证CORS、网络环境、请求中断、输出时延及手机存储。它增加一个无服务器后端依赖，并需要首次翻译联网、向第三方发送所选文本，改变了此前“全部纯本地”的翻译约束。若这些约束完全不能放宽，跨手机、免模型、自动自然整章翻译目前没有可承诺的方案，继续使用人工/外部译文导入最稳妥。

不推荐把以下方案作为公开网站的唯一基础：

- Chrome Translator API：官方说明目前只支持桌面，移动端不支持，而且首次需要下载语言模型，无法覆盖iPhone和安卓目标。[Chrome官方说明](https://developer.chrome.com/docs/ai/translator-api)
- LibreTranslate：开源自托管可用，但需要运营服务器和模型；官方公网服务生产API要付费，不能当成免费无限服务，也不能默认依赖别人公益实例。[LibreTranslate官方FAQ](https://docs.libretranslate.com/guides/faq/)
- 未公开/抓包的商业翻译接口、公共网页爬取：没有接入，不作为合法稳定的免费后端。

当前结论：**显示与比例算法已修复，自动生成译文仍未实现。** 下一阶段若采用云端免费额度路线，应先确认服务端方案与数据流，再配置和验证；本轮没有创建账号、申请密钥、发送小说或部署后端。
