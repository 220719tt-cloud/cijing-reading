# 重试只补缺口：354个缓存 + 17个未完成验收

2026-10-18。本轮未清空任何数据库、未升级数据库版本、未修改Worker、未推送或部署网站。

## 实际代码逻辑

- `useAutoTranslation.retry()`只请求重新读取缓存、允许处理已记录失败并启动任务；没有调用删除/清空接口。
- `engine.run()`每次任务开始重新读取IndexedDB并严格验证原书哈希及范围。`missingSegments()`从原文中扣掉成功缓存的源范围；队列只含缺口。不是按内存页码或显示文本猜测进度，也不是整章重新请求。
- 每个成功子批次追加到旧成功集合，校验源范围、ID和译文后事务写入；只有保存成功才报告已缓存数量。CAS比较可阻止其他页面同时改缓存时被静默覆盖。源段落、书库、阅读位置、收藏和学习库没有写入路径。
- 同一标签页的同章任务串行，连续点击产生的后续任务重新读取上一个任务已保存的结果。失败重试仍遵循既有次数预算和限流；失败输入可能有限重复，成功译文不重发。请求的必要原文上下文可能包含邻近已缓存范围，但不将其作为待翻译segments再次要求翻译。
- 刷新/任务取消后从IndexedDB持久缓存重新计算缺口；默认不会自动循环重试已经记录的失败。此处不是只保存在React内存中。正常关闭浏览器不删除数据库；用户主动清理站点数据、隐私模式和浏览器驱逐站点存储不属于应用可保证永久保留的情况。

## 进度显示改进

此前“待处理”只统计尚未记录为失败的缺口，因此17个全部为失败时显示“失败17、待处理0”，容易误以为进度重置或已经没有剩余内容。

现新增直接基于源范围缺口计算的`remaining`，UI明确显示：**已缓存354个句组，剩余待翻译17个（含失败17、其他待处理0）**。成功保存后实时递增缓存数、递减剩余数；云调用次数单独计数。

## 验证结果（不把模拟模型当云端质量证据）

- 新增`translation-retry-cache.test.mjs`，对TXT和EPUB各建354个已有成功+17个分散失败的原创测试章。拦截`clear/delete`确保任务没有删除操作；每次更新逐字段核对354个旧片段；仅17个缺口进入模型替身，旧片段不进入待翻译数组。逐批进度从354/17到371/0。
- 中途取消时358个已落库，重新打开数据库只请求剩余13个；17个缺口在两个任务中均无重复成功请求。429只发一次并保留原缓存；两个并发排队任务也只发送17个缺口一次。既有React重试/缓存重读测试同步验证剩余数。
- 全量194项自动测试通过；TypeScript检查、生产构建和静态托管检查通过。
- **当前真实EPUB章节**：重试前已缓存354、剩余17、95%。实际点击一次重试，本轮发出5次单句组请求，其中4次报告模型JSON异常，最后以通用502/“模型译文不完整”停止。本轮未产生通过校验的新译文，原354成功缓存全部保留，剩余仍17。没有自动开启第二轮重试。
- 刷新真实网页后仍为354/17、95%，本次调用0；没有从零开始或自动再次请求这17个已知失败。控制台转发仅记录请求序号和句组数，不记录私人小说正文或模型原始输出。

结论：缓存复用与只补缺口已通过自动化和当前网页验证；本轮不声称17个顽固句组已翻译成功，也不声称无限免费/任意模型输入必定成功。模型输出错误的进一步修复应作为单独任务处理。
